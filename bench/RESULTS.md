# 实测结果（2026-10-12）

环境：Apple M4（10 核）/ 16GB，JDK 17，MySQL 8 + Redis 7 + Nacos + RocketMQ（docker compose），aggregation-service 单机或双节点，k6 v0.54.0。
数据：项目自带种子数据（G39 一等座 140 张，北京→杭州 4 趟车）。复现：`bash bench/run-all.sh`。

## 实验 1：车票查询多级缓存（单节点，50 并发，每组 30s，组前 10s 预热）

| 组 | 方案 | 线路 | QPS | 平均 | P99 | 每请求 Redis 命令 | L1 命中率 |
|---|---|---|---|---|---|---|---|
| A | v1 原始实现（逐车次 GET 票价、逐席别 HGET 余票） | 北京→杭州 | 409 | 121.9ms | 634.7ms | 21 | — |
| B | v2 Pipeline | 北京→杭州 | 1,837 | 27.0ms | 136.7ms | 21 | — |
| C | v3 Caffeine L1 + 余票一次 Pipeline | 北京→杭州 | 3,371 | 14.0ms | 100.4ms | 14 | 100% |
| D | v3 去掉余票读取（定位开销） | 北京→杭州 | 9,549 | 4.3ms | 43.6ms | 0 | 100% |
| E | v1（无车次线路，每次加锁回源 DB） | 杭州→北京 | 207 | 240.4ms | 1,145.3ms | 20.8 | — |
| F | v3（空列表本地缓存） | 杭州→北京 | 24,363 | 1.8ms | 14.3ms | 0 | 100% |

- v1 → v3：QPS ×8.2，P99 −84%；仅本地缓存的增量（B → C）：QPS +84%。
- 余票读取（14 次 HGET，一次 Pipeline）是 v3 剩余的主要开销，去掉后 QPS 再 ×2.8。

## 实验 2a：双节点本地缓存失效广播（100 轮调价）

| 指标 | 结果 |
|---|---|
| 节点 A 调价返回 → 节点 B 读到新价（端到端） | P50 11.5ms，平均 28.7ms，P99 127.9ms |
| Pub/Sub 发布 → 节点 B 完成本地失效 | P50 0.98ms，平均 1.47ms，P99 17.2ms |
| 第一次读即新值 | 99%（共 2 次旧值读取，0 次超时） |

## 实验 3：订单基因法分片路由（单元测试，10 万样本）

- 修复前：订单号基因位未补零，9.89% 的用户 `userId % 1000000 < 100000`，8.89% 的订单按 order_sn 路由到与 user_id 不同的分表（取消、关单、支付回调查不到订单）。
- 修复后（`String.format("%06d", ...)`）：错误路由 0，边界基因 000000 / 000007 / 099999 / 100000 均正确。

## 过程中发现并修复的环境问题

- Docker 初始化导入种子 SQL 时，容器内 mysql 客户端按 latin1 读取 UTF-8 文件，导致中文二次编码：`bench/fix-db-charset.sh` 只修复能按 latin1 原样往返的字段，修复后 140 张表与正确导入逐表校验和一致。
- Lombok 1.18.30 不支持 JDK 25：脚本自动切换到 JDK 17/21。
