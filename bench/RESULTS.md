# 实测结果（2026-10-12 ～ 10-13）

环境：Apple M4（10 核）/ 16GB，JDK 17，MySQL 8 + Redis 7 + Nacos + RocketMQ（docker compose），aggregation-service 单机或双节点，k6 v0.54.0。
数据：项目自带种子数据（G39 一等座 140 张，北京→杭州 4 趟车）。复现：`bash bench/run-all.sh`。

## 实验 1：车票查询多级缓存（单节点，50 并发，每组 30s，组前 10s 预热）

| 组 | 方案 | 线路 | QPS | 平均 | P99 | 每请求 Redis 命令 | L1 命中率 |
|---|---|---|---|---|---|---|---|
| A | v1 原始实现（逐车次 GET 票价、逐席别 HGET 余票） | 北京→杭州 | 409 | 121.9ms | 634.7ms | 21 | — |
| B | v2 Pipeline | 北京→杭州 | 1,837 | 27.0ms | 136.7ms | 21 | — |
| C | v3 Caffeine L1 + 余票一次 Pipeline | 北京→杭州 | 3,371 | 14.0ms | 100.4ms | 14 | 100% |
| D | v3 去掉余票读取（定位开销） | 北京→杭州 | 9,549 | 4.3ms | 43.6ms | 0 | 100% |
| E | v1（无车次线路，每次加锁回源 DB） | 杭州→北京 | 207 | 240.4ms | 1,145.3ms | 20.8 | — |
| F | v3（空列表本地缓存） | 杭州→北京 | 24,363 | 1.8ms | 14.3ms | 0 | 100% |

上表为首轮单次结果。之后同一环境重复 3 轮（`run-query-repeat.sh`），以 3 轮中位数为准：

| 组 | 方案 | QPS 中位数（最小～最大） | P99 中位数（最小～最大） | 成功率 |
|---|---|---|---|---|
| A | v1 | 709（484～752） | 251.4ms（158.4～383.7） | 100% |
| B | v2 Pipeline | 1,893（1,711～2,040） | 106.2ms（99.0～125.5） | 100% |
| C | v3 Caffeine L1 + Pipeline | 5,301（5,179～7,188） | 38.6ms（26.5～42.1） | 100% |
| D | v3 去掉余票读取 | 13,535（12,743～17,431） | 26.0ms（20.2～28.6） | 100% |
| E | v1 无车次线路 | 257（198～265） | 1,125.7ms（846.7～1,372.1） | 100% |
| F | v3 无车次线路 | 17,902（14,541～22,344） | 18.6ms（15.2～25.1） | 100% |

- 仅本地缓存的增量（B → C）：QPS 1,893 → 5,301（+180%），P99 106.2 → 38.6ms（−64%）；三轮中 C 组最低值 5,179 仍高于 B 组最高值 2,040。
- 余票读取（14 次 HGET，一次 Pipeline）是 v3 剩余的主要开销，去掉后 QPS 再 ×2.6。
- 首轮单次与 3 轮中位数差异明显（C 组 3,371 vs 5,301），说明单轮数据受 JIT 预热、机器负载影响较大，引用时以 3 轮中位数为准。
- 局限：节点、中间件、k6 在同一台机器上，三者争抢 CPU。

## 实验 2b：双节点并发抢票（500 个用户，50 并发，库存 140）

修复 3 个并发缺陷后的最终结果：

| | v1 车次级分布式锁 | v2 令牌桶 Lua + 车次席别两级锁 |
|---|---|---|
| 售出 / 库存 | 140 / 140 | 140 / 140 |
| DB 车票数 / 重复座位 | 140 / 0 | 140 / 0 |
| 令牌桶剩余 / 余票缓存剩余 | — / 0 | 0 / 0 |
| 返回「余票不足」 | 360 | 360 |
| 其他失败 | 0 | 0 |
| 平均 / P99 | 2,257ms / 21,272ms | 1,523ms / 7,562ms |
| 吞吐 | 18.0 req/s | 26.7 req/s |

更正：这 360 个「余票不足」中混有缓存冷启动时的误拒（见实验 7 与缺陷表第 4 行），当时 50 个并发请求同时加载余票缓存，只有 1 个能拿到真实余票，其余在仍有票时被拒；由于后续请求补满了 140 张，售出总数没有暴露这个问题。修复后的验证见实验 7。

### 压测中发现并修复的原项目并发缺陷

| 缺陷 | 现象（修复前） | 修复 |
|---|---|---|
| 售罄临界点可用车厢为空，`carriage_number in <foreach>` 拼出 `in group by` 非法 SQL | v1 49 次 ShardingSphere 解析异常，作为系统异常返回 | `SeatServiceImpl.listSeatRemainingTicket` 空列表直接返回空，走「余票不足」 |
| `TrainSeatTypeSelector.distributeSeats` 捕获所有 `ServiceException` 改写为「车型暂未适配」 | 上一项修复后，同样 49 次被误报为「当前车次列车类型暂未适配」 | 只在选座策略不存在时提示未适配，业务异常原样抛出 |
| 令牌桶冷启动 `tryLock()` 不等待 | v2 8 次「购票异常，请稍候再试」 | 改为最多等待 3 秒，拿锁后双重检查 |

| 余票缓存加载二次检查命中时返回空结果：排队等锁的请求拿到锁后发现缓存已构建，`SeatMarginCacheLoader#load` 却返回空 Map，调用方当作余票 0 | 实验 5（100 人 / 库存 140 / 20 并发）两组均有 19 个请求在有票时被拒「列车站点已无余票」 | 二次检查命中时返回缓存中的余票（先提交失败的单测 63e0762，再修复 4c2671e） |

修复过程（同一套脚本、同一份数据）：v1 其他失败 49 → 49 → 0，v2 其他失败 8 → 0 → 0。

## 实验 4a：异步关单时效（RocketMQ 延迟级别临时改为 1s，50 个未支付订单，双节点）

| 指标 | 结果 |
|---|---|
| 延迟到期 → 座位 / 余票缓存 / 令牌回滚完成（已扣除 1s 延迟） | 平均 0.90s，P50 0.54s，P99 2.65s，最大 6.43s |
| 最终状态（令牌 / 余票缓存 / 锁定座位 / 已关单 / 待支付） | 140 / 140 / 0 / 50 / 0：全部精确恢复，无多还、少还 |

说明：默认延迟级别为 14（10 分钟），压测通过 `--order.delay-close.level=1` 缩短；耗时从订单服务发出消息时（`MessageWrapper.timestamp`）计起。

## 实验 6：自研 Redis Lua 固定窗口限流（同一个 key，上限 50）

| 层级 | 条件 | Lua 原子实现放行 | 非原子 GET → INCR 放行 |
|---|---|---|---|
| 脚本级 | 真实 Redis，50 并发 × 500 次，3 轮 | 50 / 50 / 50 | 59 / 60 / 61 |
| 应用级 | 两个应用节点交替，50 并发 × 500 次，3 轮 | 50 / 50 / 50（Redis 计数均为 500） | 69 / 98 / 76 |

- 窗口重置：上限 5、窗口 1s，节点 A 连续 10 次放行 5 次；等待 1.2s 后节点 B 连续 10 次放行 5 次。
- 非原子实现在应用层超发更严重（最多 +96%），因为 GET 与 INCR 之间多了一次网络往返，竞态窗口更大。

## 实验 4b：关单消息重复投递（20 个未支付订单，每单并发投递 5 次，双节点）

| 投递方式 | 投递次数 | 实际回滚次数 | 令牌 / 余票缓存 | 锁定座位 | 已关单 / 待支付 |
|---|---|---|---|---|---|
| MQ 重投（消息体相同，靠 `@Idempotent` 拦截） | 100 | 20 | 140 / 140 | 0 | 20 / 0 |
| 业务重复发送（每次新消息，靠订单状态条件拦截） | 100 | 20 | 140 / 140 | 0 | 20 / 0 |

两种方式下每单只回滚一次，令牌与余票没有被重复归还。

## 实验 5：下单失败补偿（注入 20% 订单创建失败，100 个用户，库存 140，20 并发，双节点）

| 补偿 | 成功 | 注入失败 | DB 车票 | DB 可售座位 | 令牌 | 余票缓存 | 令牌少计 | 余票少计 |
|---|---|---|---|---|---|---|---|---|
| 关闭（原实现） | 63 | 18 | 63 | 77 | 59 | 59 | 18 | 18 |
| 开启 | 59 | 22 | 59 | 81 | 81 | 81 | 0 | 0 |

- 关闭补偿时，每次下单失败都让缓存永久少计 1 张：18 次失败后有 18 个座位实际可售却无法卖出；开启后缓存与 DB 完全一致。
- 两组中另有 19 个请求在有票时被拒，由此定位到余票缓存冷启动缺陷（见实验 2b 缺陷表），修复后待 `run-verify-fix.sh` 重跑确认。

## 实验 6（续）：限流接入真实查票接口（双节点，各 150 次，共 300 次）

| 配置 | 节点 A / B 请求 | 放行 | 被限流 | 错误 |
|---|---|---|---|---|
| 开启，每秒 20 次（未登录按 IP，两节点同一个计数 key） | 150 / 150 | 20 | 280 | 0 |
| 关闭（默认） | 150 / 150 | 300 | 0 | 0 |

两个节点合计只放行 20 次，说明计数在 Redis 中共享，而不是每个节点各放行 20 次；关闭时查询完全不受影响。

## 实验 3：订单基因法分片路由（单元测试，10 万样本）

- 修复前：订单号基因位未补零，9.89% 的用户 `userId % 1000000 < 100000`，8.89% 的订单按 order_sn 路由到与 user_id 不同的分表（取消、关单、支付回调查不到订单）。
- 修复后（`String.format("%06d", ...)`）：错误路由 0，边界基因 000000 / 000007 / 099999 / 100000 均正确。

## 过程中发现并修复的环境问题

- Docker 初始化导入种子 SQL 时，容器内 mysql 客户端按 latin1 读取 UTF-8 文件，导致中文二次编码：`bench/fix-db-charset.sh` 只修复能按 latin1 原样往返的字段，修复后 140 张表与正确导入逐表校验和一致。
- Lombok 1.18.30 不支持 JDK 25：脚本自动切换到 JDK 17/21。
